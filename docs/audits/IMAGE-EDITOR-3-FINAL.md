# IMAGE-EDITOR-3 — final integration audit (3/3)

Baseline: `main` at `bb48853a69b35b422ee63e27fc27892251bc2ff9` (2026-10-12).
Predecessors: PR #754 (editor/article rendering), #762 (six entity integrations), #769 (0122 D1 migration hotfix). No new data architecture or migration.

## Presentation and precedence

1. Explicit per-slot image-display JSON (`thumbnailImageDisplay` / `detailImageDisplay`) wins over defaults.
2. Historical article/event `image_display` and focal-point values remain readable when no JSON override exists.
3. Otherwise thumbnail uses `DEFAULT_THUMBNAIL` (`auto`) and detail `DEFAULT_DETAIL` (`natural`). Legacy article settings are cleared in existing article save payloads. Event reset saves explicit automatic defaults when the event still has a legacy cover/contain value.
4. The thumbnail renderer reads **intrinsic dimensions** after image load and measures the **actual rendered frame ratio**; EXIF-rotated images use the browser's decoded intrinsic orientation. No inference from URL or filename.
5. For landscape cards: `cover` for well-matched landscape photos; `contain` plus blurred backing when aspect mismatch risks heavy crop, including portraits in landscape slots and squares in wide slots. Bright-background artwork (e.g. posters) also retains the historic `contain` behavior using the existing 40×40 sample, when canvas access is allowed. Missing/cross-origin samples fall back to the dimension rules.
6. `crop` always fills and uses manual focal X/Y and zoom; `blur` preserves uncropped foreground with CSS blurred, decorative `aria-hidden` background; `natural` on detail shows the entire image at its natural aspect ratio.
7. Image change creates a new automatic-fit decision for the new `src`; a stale decision is never reused for the replacement.
8. The fixed-size SSR frame is rendered consistently during hydration. When image dimensions become known, the fit changes without changing thumbnail geometry. A brief change from crop to blur may be visible on exceptionally fast cached images.

## Performance and failure handling

- The foreground and decorative blurred background use the **same `src`, `srcSet`, `sizes` and loading policy**, so responsive image choice can use browser caching; no extra API or R2 image rendition is generated by this feature.
- Reduced CSS blur from 24px to 18px and scaling from 1.14 to 1.09 to limit overdraw. This is a code-level optimization, **not a measured benchmark**.
- The existing `SmartCardImage` 40×40 light-background sampling is reused *only for automatic fits*, so posters do not regress to an unwanted crop. The sample is cached by source and natural dimensions to avoid repeated canvas reads after a mode change; there is no new server-side image processing. Explicit manual modes do not sample.
- `loading="lazy"` stays on offscreen cards; detail and relevant above-the-fold images continue to use eager/high priority when already configured by callers. Natural detail image dimensions remain content-driven, while cards preserve their layout ratio.
- Event-image 404/network failures still use the category-specific fallback. Other sections preserve their existing fallback handling; there is no new generic dog image.
- Missing URLs are handled by the existing query/card contracts. Server-side validation of remote image URLs or universal HTTP error fallbacks has **not** been added.
- New manual settings survive storage through the pre-existing API and database JSON columns; no destructive changes to R2 images, Notion integration or gallery content.
